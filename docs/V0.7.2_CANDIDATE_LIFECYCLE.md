# v0.7.2 候选生命周期重构

## 背景

多轮编辑原本默认把上一版候选与最近要求全部带入下一轮。这适合“再克制一点”式微调，但当用户提出一个独立的新目标时，旧候选会继续影响模型。模型若返回分析、摘要或严重残缺正文，插件虽然能检测到覆盖率不足，却仍把残片登记成正常候选轮次，并允许它占据主工作流。

另一个界面问题是“候选摘要”直接展示供应商原始返回，而“新版本”展示经过逐块决策合成的文本，两者并非同一份内容，容易让用户误以为发生了串轮或错误应用。

## 产品原则

1. **任务起点必须明确**：已有候选后，用户可以选择“继续当前版本”或“从原文开始新任务”。
2. **失败不能冒充成功**：严重缺失、无法覆盖保护区的正文进入“失败尝试”，不新增正常轮次，也不替换当前有效候选。
3. **界面展示同一事实**：正常轮次的摘要来自本地逐块合成后的实际候选，并标注生成阶段和任务起点。
4. **用户保留最终权力**：失败残片仍可通过高级入口显式载入为可编辑草稿；载入与应用均给出明确风险提示。
5. **检查不依赖特定模型**：隔离规则只使用正文边界、覆盖率和本地对齐结果，不使用角色名、世界书格式或模型专属措辞。

## 状态模型

### 正常轮次

只有满足以下条件的结果才能进入正常轮次：

- 存在可用正文；
- 能覆盖原文中应保留的主体内容；
- 即使缺少正文结束标记，也至少已通过覆盖检查，并明确标记为“边界不完整”。

正常轮次保存：本轮要求、实际合成候选、供应商原始候选、任务起点、来源阶段、完整性状态和影响计划。

### 失败尝试

以下情况进入失败尝试：

- 只返回分析、摘要或空正文；
- 初稿与完整性修复后仍严重缺失；
- 超时或取消前只得到无法覆盖保护区的正文残片。

失败尝试不会改变 `candidate`、`requirements` 或正常 `turns`，因此后续保存仍指向最后一个有效候选。失败记录只保存在当前工作台会话，不写入聊天消息。

### 任务起点

- `current`：使用当前合成候选作为工作稿，并携带此前正常轮次要求。
- `original`：以捕获时的原消息为唯一工作稿，不发送旧候选和旧轮次要求。成功后开启新的正常轮次链；失败时保留旧链，便于恢复。

第一次生成没有现存候选，自动等同于 `original`。

## 界面

- 存在有效候选时，在输入框上方显示“本轮从哪里开始”。
- 正常轮次显示“实际候选摘要 · 阶段 · 起点”。
- 失败尝试收纳在独立的折叠区，显示失败原因、残片摘要和“强制载入为可编辑草稿”。
- 强制载入后默认进入完整预览，标注高风险；应用时再次确认。

## 验收标准

- “从原文开始新任务”的提示不包含旧候选和旧轮次要求。
- 覆盖率不足的结果不会新增正常轮次，不会清空用户当前要求，也不会替换有效候选。
- 正常轮次摘要与可应用的合成候选一致。
- 完整性修复稿和初稿具有可见来源标记。
- 用户可以显式载入失败残片并在确认风险后保存。
- “应用为新版本”仍只由用户点击触发，且保存为新 Swipe。
- 既有选区修改、逐块确认、超时取消和诊断日志测试不回退。
